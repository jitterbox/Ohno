0.1.3 15 August 2026 Algorithmic complexity for C#

A research pass against the current Roslyn platform, and the six phases of work it recommended. The theme is honesty about what is and is not known: constant time now has to be established rather than assumed.

O(1) was a fallback

Any System.* member whose containing type was not itself a collection was costed as free. System.Linq.Enumerable is a static class, so every LINQ overload missing from the catalog was silently constant — a sort could disappear from the headline entirely.

Reported before, and what the call actually costs
Call Reported Actual
.OrderBy(k, comparer) O(1) O(n log n)
.Sum(selector) O(1) O(n)
.Concat, .Zip, .Union O(1) O(n + m)
File.ReadAllLines(path) O(1) O(file)

Meanwhile string is a collection by that same test, so Substring and Split took the opposite path and dragged ordinary methods to Low confidence — two wrong answers in opposite directions from one incidental type check.

Constant time is now something the analyzer has to know: a catalog entry, or an allowlist entry keyed by containing type rather than member name, because int.GetHashCode() is Θ(1) and string.GetHashCode() is Θ(length). The rule covers calls, constructors, metadata property reads, and bodyless method symbols.

The toolchain was broken where CI could not see it

The analyzer solution is Ohno.Complexity.slnx, which the .NET 8 SDK cannot parse — dotnet restore fails outright. CI passed only because hosted runners carry newer SDKs than the workflow declared, so the declared toolchain and the working toolchain had quietly drifted apart. Anyone with just the declared SDK could not build at all.

Resolved

All projects on net10.0, CI declaring 10.0.x, and a global.json pinning the SDK so the drift cannot recur silently. The Roslyn package reference is unchanged — 5.6.0 already ships net10.0 assets.

Bounds that moved, and why

Three results changed by design. Each is a correction toward the documented model, not a loosening of it.

  • Sliding window — O(n) O(k + n). Reserving k slots is Θ(k) work, and k is independent of n. The old result assumed k ≤ n, which the model forbids.
  • Insertion sort — O(n) O(n²). The amortized-pointer rule holds only while the inner counter keeps its position between outer steps, and j = i - 1 re-seeds it. Every two-pointer case in the bench is unchanged.
  • Constant inner loop — O(n²) O(n). A literal ceiling on a constant-stepping counter is a fixed count; a literal ceiling on a halving variable still yields log.

Also fixed

  • Selection and document analysis cancelled each other. Both are Fast and both arrive on the same method, and a single shared cancellation slot meant an edit with an active selection had the document request cancel the selection every time.
  • .slnx was invisible to the extension, so Ohno could not analyze its own repository project-backed.
  • Accessors, indexers, and operators were never reported despite the protocol already declaring the kinds. An expensive getter is one of the easiest places for an O(n) to hide.
  • No depth guard on the operation walk. Generated code can nest far enough to overflow the stack — and that stack belongs to a server process shared by the whole editor session.
  • Non-backtracking regex earns a real bound. The one place the honesty rule points toward a tighter answer, since .NET guarantees that engine scans the input once.

How it was sequenced

  1. Toolchain and harness. Baseline recorded before any edit; .NET 10 migration; benchmark ceilings.
  2. BCL accuracy. The O(1) rule, and the catalog surface that made the old fallback load-bearing.
  3. Analyzer cost. Seven duplicated walkers collapsed into one. No result permitted to change.
  4. Robustness. Keyed cancellation, a token inside the walk, a depth floor.
  5. Coverage and UX. Solution discovery, accessors, warning noise.
  6. Research-backed additions. Regex engines, and a bench widened at the boundary the literature flags.

Deliberately not done

Deferred, with reasons recorded

Simplify placement is the one refactor that could change output, and the benchmark on the test machine varies twofold run to run — there is no way to show it helps. Spending correctness risk on an unmeasurable gain is the wrong trade.

CFG ranking functions and the AnalyzerUtilities dataflow engine were considered and not scheduled. Both are real improvements with real costs, and neither is needed for the work above.

The widened bench was meant to carry no engine risk. It found two real bugs instead, which is the better outcome — both are in “bounds that moved”.
